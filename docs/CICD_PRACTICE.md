# 第一轮练习：CI 验证 + 手动新增列

目标数据库是 Ubuntu 上既有的 `Project1Db`。这份检查单不是执行授权：
本轮本地改动不连接服务器、不执行生产 SQL、不触发部署。

## 本轮变更

- 新迁移：`20261010171840_AddProductCicdPracticeNote`。
- 只新增 `dbo.Products.CicdPracticeNote nvarchar(100) NULL`，没有默认值、回填或删除。
  既有产品的新字段默认是 `NULL`；原 `Products.Note` 和历史迁移保持不变。
- 产品 API 的创建、更新和查询支持 `cicdPracticeNote`；空白输入保存为 `null`，
  非空输入去除首尾空格，请求最多 100 字符。现有产品权限不变。
- Products 页面新增 **CI/CD practice note** 输入框和列表列，支持搜索；
  重新启用产品时保留该备注。
- CI 使用一次性 SQL Server 数据库验证升级和重复执行，不运行生产迁移。

## 操作顺序

1. 本地检查改动，放到新的练习分支，提交并推送 PR。等待前后端两项 CI 成功后再合并。
2. 等待合并后的 **Project1 CI / main / push** 全部成功。
   记录完整 commit SHA、CI run ID 和 attempt；本轮 SQL 与应用必须使用同一版本的产物。
3. 在 **Project1 manual deployment** 中只勾选 `check_migrations`，
   保持 `deploy` 未勾选，运行只读历史预检查。
   若服务器仍在已有 `Note` 的基线，预期只有本轮一个待执行迁移；
   实际有其他待执行项或结构不符时停止，重新审阅完整范围。
4. 下载对应的 `project1-migrations-sql-<SHA>`，核对来源、清单和哈希，
   审阅待执行部分确实只新增练习列。
5. 按[手动迁移检查单](MANUAL_MIGRATIONS.md)确认目标、执行身份、维护窗口，
   完成新的可恢复备份后，由管理员单独确认并手动执行审阅过的 SQL。
   原历史查询账号不自动获得写入权限；密码不放进命令行、Git 或聊天。
6. 核对列类型、可空性、迁移历史和旧产品数据。再次运行只读预检查，预期待执行为 0。
7. **确认数据库迁移成功后**，用同一 CI run 的应用产物运行应用部署：
   勾选 `deploy`，取消 `check_migrations`。这一步只更新前后端并重启 API。
8. 检查 API 健康状态；在 Products 页面验证旧记录显示空备注、新增/编辑备注、
   刷新后仍保留、清空后为 `null`、100 字符边界和重新启用行为。
   保留原产品与业务数据，不拿已有字段做删除练习。

新增可空列兼容旧版本应用；**新 API 依赖此列，不能在迁移之前部署**。
应用回滚不应删除已新增的列；代码回滚也不等于数据库回滚。

## 第二轮删除练习（尚未实施）

第一轮验证完成后另开 PR：先移除前后端对练习字段的依赖并部署，
再在独立确认、备份和审阅后手动删除 **仅 `CicdPracticeNote`**。
删除会丢失该列中的练习备注；不能删除原 `Note`、业务列或历史迁移。
不要直接对现有库运行降级来代替这套分阶段流程。
