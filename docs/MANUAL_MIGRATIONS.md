# 生产数据库：CI 验证 + 手动迁移

CI 验证并发布 SQL，管理员决定何时执行生产迁移。
GitHub 不上传或执行 SQL，应用 CD 不自动迁移；本检查单不代表执行授权。

## 1. 固定版本与待执行范围

1. 选择全部成功的 `Project1 CI / main / push`，记录完整 SHA、run ID、attempt 和运行链接。
2. 下载 `project1-migrations-sql-<SHA>`，核对 build-info、迁移清单与哈希。
   使用本次清理合并后的新 CI 包，旧的自动执行批准说明不再受包验证器支持。
3. 向 Ubuntu 管理员私有的新操作目录传输文件，再核对哈希；不覆盖旧操作目录，
   不上传数据库密码或应用配置。在该目录可运行：

   ```bash
   sha256sum -c SHA256SUMS
   ```

4. 用[只读预检查](MIGRATION_PRECHECK.md)比较历史。
   待执行为 0 且真实结构符合预期时不需要迁移，只考虑应用部署。
   历史缺项、有未知项或不是清单的完整前缀时停止，不能伪造历史记录来跳过检查。

执行前再次核对服务器 `homelab-server`、数据库 `Project1Db`、库状态、真实结构和历史。
旧报告仅代表查询时刻，不验证所有表/列，也不会阻止其他管理员操作。

## 2. 审阅与演练

- 审阅待执行迁移的删除/改名、非空列、默认值、数据转换、回填、索引、锁和预计耗时。
  确认实际结构符合起点，幂等 SQL 不是结构漂移修复工具。
- 在隔离测试库或受保护的恢复副本演练，检查结构、历史和业务数据。
  CI 的 Note 升级回归不能替代新迁移的演练。
- 确认新旧应用兼容性、维护窗口、停止写入方式和部署先后顺序。
  破坏性变更不能假定“先迁移再部署”总是安全。
- 指定唯一操作人；SQL 脚本没有 EF 迁移锁，GitHub 并发组也管不到手动终端。

## 3. 备份、恢复与权限

- 执行前创建当前目标库的新完整备份，启用 checksum，核对完成状态、数据库、位置和可读性。
  记录时间并保存在受保护位置。
- 检查备份并在隔离库实际恢复演练，确认恢复权限、空间和应用切换步骤。
  `RESTORE VERIFYONLY` 不是完整恢复测试，也不验证数据库内所有数据结构。
- 单独确认执行身份和本次 SQL 所需权限。现有 `project1_migrate` 仍是历史只读账号，
  不用于执行、不自动追加写权限；应用账号不应因此获得 DDL 权限。
  不默认授予 sysadmin/db_owner。
- 密码不放在 Git、工作流、命令行参数或聊天截图里。

没有可恢复备份、目标确认、维护窗口或执行权限时，停在这里。

## 4. 管理员手动执行

在 Ubuntu 私有操作目录使用已审阅的 `migrations.sql` 和受信任的 SQL 工具，
以单独确认的身份执行，不临时重新生成另一份 SQL。
具体命令在确认账号、文件路径、备份和迁移范围后逐步确定，不复制旧自动执行器命令。

若使用现有 ODBC sqlcmd，审阅 `-b` 的错误退出行为以及登录/查询超时；
不要忽略错误。密码通过交互提示等受控方式输入，不放在 `-P` 参数里。
错误退出不等于全文件原子回滚：同段后续语句可能继续执行，早先已提交的迁移仍可能存在。
不要随意给整份文件添加外层事务，不修改历史表伪造成功。

错误、超时或断连时，停止后续应用部署，不盲目重跑、不跳到后续片段、不自动恢复。
先检查活动会话、事务、结构、历史和数据，判断哪些操作已经提交，
再由管理员决定经审阅的修复或恢复。恢复可能丢失备份后的写入，需先确认影响。

## 5. 验证与归档

重新核对历史、新表/列/索引和关键数据；按兼容性方案执行既有 API/前端部署，
检查健康端点和相关业务读写。归档来源、SQL、清单、哈希、备份位置、执行时间和验证结果；
敏感日志不提交到仓库。代码回滚不会回滚数据库，降级或恢复需要另行审阅。

## 仓库清理不等于服务器卸载

仓库移除了自动执行器、宿主、批准/账本、备份协调及对应 CI 验收。
既有 EF 历史迁移保留；不卸载 Ubuntu 文件、不改账号、sudoers、密码或数据库。
已安装的只读 status 和应用部署工具继续保留。
若曾另行安装自动迁移工具，应先由管理员盘点，再单独审核停用方案。
